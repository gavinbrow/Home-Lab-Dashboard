# Workspace tool path contract alignment

All workspace file tools (list_files, read_file, write_file, apply_patch, verify_file and publish_artifact) now offer the same portable relative-path syntax enforced by rooted storage. The JSON schema contains a representable portable-syntax pattern and examples such as report.txt and outputs/result.bin. Runtime refinement also calls the actual exported storage relativePath helper. No path is stripped, normalized, reinterpreted or rewritten. The 4096 runtime length bound uses UTF-16 code units, explicitly described in every offered path. JSON Schema maxLength uses Unicode code points and can therefore accept an astral string that canonical runtime validation rejects; full length-metric equivalence is not claimed.

The empty string names the root only for list_files; dot is rejected. Paths use forward slashes and reject absolute/drive/UNC paths, traversal/dot/empty components, backslashes, C0/DEL controls, colons, reserved punctuation, trailing component dots/spaces, Windows device components (case insensitive, including extensions and the existing digit/superscript variants), and values longer than 4096 JS characters. Unicode names, hidden components and internal spaces remain allowed. Host root/symlink/access controls still independently enforce actual IO.

Complete invalid model proposals use existing persisted rejected-tool feedback and never dispatch. Legacy unstarted file calls receive bounded invalid_tool_arguments with executed:false. Already dispatched operations are reconciled under their original operation IDs, rather than discarded because a newly tightened proposal schema would reject their original argument.

## Missing-verification completion feedback — analysis only

Current behavior retains a known completed model turn, runs configured fixed verification commands when present, and then fails required_verification_missing if mandatory verification has no actual evidence. It never treats prose as proof or automatically retries an ambiguous inference. This remains unchanged in the path candidate.

A bounded future correction could persist a completion-rejected controller step referencing the exact completed inference, then admit at most one or two fresh corrective model rounds using the ordinary current grant/profile/capability/secret gates and remaining wall-time, tool-step, output and hard-token budgets. The controller message must be explicitly identified as controller feedback; it must not invent a tool-call ID or human message. A durable per-inference marker and job-wide correction count prevent crash/recovery duplication and infinite no-tool loops. The final verification requirement remains identical. If no permitted verification tool exists, budgets are exhausted, the profile is revoked, or the inference/host outcome is unknown, fail or reconcile immediately instead of asking the model to invent evidence. Earlier failed checks remain retained; a later pass may supersede only the same verification identity/target.

This could improve robustness after a known complete no-tool answer, but it does not itself establish artifact requirements that are absent from a profile/task contract and does not repair model quality by bypassing scope. It requires separate authorization and focused tests (one correction succeeds; repeated no-tool answer exhausts fixed bound; cancellation/revocation/budget failure causes no generation; restart after persisted feedback does not duplicate correction; no unknown operation is replayed). No such feedback implementation or autonomous model campaign is included here.
