# Project and retained storage

Mutable project roots belong to the enrolled storage host. API/worker code must use a `WorkspaceFileAdapter` that delegates to the host's rooted file service; a Windows or Linux canonical path is never opened on the control-plane filesystem. Without a configured adapter, file operations report `capability_unavailable`.

`BlobStore` is exclusively for service-owned retained bytes. Set `ARTIFACT_ROOT` to a durable protected mount, outside editable project roots, with no project execution identity write access to that mount or its ancestor directories. Never place it in an API/container writable layer. Its local filesystem checks are defense in depth within this trusted service directory; they are not an untrusted host-folder confinement boundary. Back up the database and every referenced hash object together. There is no automatic deletion or garbage collection in this package.

Uploads are bounded, checksum-verified and atomically published with an exclusive hard link. Existing objects are never overwritten, and every download rechecks SHA-256. The storage filesystem must support same-directory hard links; unsupported storage fails rather than falling back to non-atomic publication. Default individual objects and ZIP exports are limited to 64 MiB. Failed capture may leave unreferenced immutable blobs; reference-aware retention is required before cleaning them.

The Linux store flushes file contents and the publication directory before success. Windows local tests exercise functional behavior only; Windows directory flush/power-loss behavior has not been verified and is not advertised as a supported production control-plane durability guarantee.

Checkpoints capture all supplied regular files, including dotfiles, ignored/untracked files and binary content. A symlink is metadata only and is never dereferenced. Host snapshot adapters must identify external edits and return `best_effort` when quiescence cannot be established. The manifest records exclusions and consistency; neither the application writer lock nor a directory scan constrains desktop/local applications.

ZIP exports contain immutable checkpoint files and `.homelab-export-manifest.json`. Directory modes and symlink targets are represented in the manifest, not recreated by ZIP entry attributes. The archive is portable transfer, not an NTFS ACL, service or database backup. Duplicate names including case collisions, dangerous Windows names, path escapes and a conflicting manifest filename fail explicitly. ZIP32 and bounded memory are intentional initial limitations.

Restart/rebuild/remove environment act on runtime resources only. Their API handlers call the signed enrolled host broker, retain a pre-operation checkpoint, and verify storage identity and file hashes afterward. A rebuild requires a different actual runtime ID and a higher generation; restart preserves runtime identity. Archive/unregister/reactivate use signed host binding transitions and persist the host-owned revision. Existing workspace/project identities and history are retained. Delete-files quarantines recoverable bytes; exact-root data deletion additionally requires a separate protected host grant and archives the binding. No generic reset performs deletion. Missing host configuration remains an explicit prerequisite, rather than a synthetic lifecycle success.

## API and policy scopes

All routes are authenticated under `/api/v1`. IDs refer to a registered workspace, with storage machine and canonical path returned for display. Entity ownership is checked in SQL; file operations additionally require a persisted `grant_id`.

| Operation | Route | Scope and input |
|---|---|---|
| List projects | `GET /projects` | Owner's registered workspaces, bounded to 200 |
| Discover roots | `GET /project-roots?machine_id=...` | Owner's enrolled machine; returns protected host-configured bindings only |
| Register | `POST /projects` | `name`, `machine_id`, `host_workspace_id`, optional `description`; validates the actual binding and captures an initial checkpoint without moving files |
| Current binding | `GET /projects/:id/binding` | Host path, read/write capability, authoritative revision and environment generation |
| List/read/search files | `GET /projects/:id/files` | `file.read`; `path`, `mode=list|read|search`, `grant_id`; list uses `limit` (max 500), `cursor`, `include_hidden`; search uses `q`, max 100 results with explicit truncation; read returns base64/hash/size |
| Conditional save/upload | `PUT /projects/:id/files` | `file.write`; `path`, `content_base64`, `expected_sha256`, `grant_id`, stable `operation_id`; null expected hash means create-only; bounded 16 MiB and host-staged publication |
| Move/create directory | `POST /projects/:id/files/rename`, `/directories` | `file.write`; rename uses `source_path`, `destination_path`, `expected_sha256`; directory creation uses `path`; both require grant and stable operation IDs |
| Preview/download | `GET /projects/:id/preview`, `/files/download` | `file.read`; path/grant; HTML/SVG remain text data, Markdown source is never executed, CSV/JSON previews are bounded, downloads force attachment |
| Instructions | `GET/PUT /projects/:id/instructions`, `GET .../history` | Versioned project configuration; PUT uses `instructions`, `expected_revision`; job snapshots retain their selected revision |
| Checkpoint | `POST /projects/:id/checkpoints` | `checkpoint.create`; `grant_id`; best-effort capture disclosed |
| List checkpoints | `GET /projects/:id/checkpoints` | Owner's metadata, bounded to 100 |
| Review changes | `GET /projects/:id/checkpoints/:checkpointId/diff?against=:beforeId` | Owner's checkpoint metadata; added/deleted/modified entries |
| Retain output | `POST /projects/:id/artifacts` | `artifact.retain`; `path`, `expected_sha256`, `grant_id` |
| Download output | `GET /artifacts/:id/download` | Owner check; hash-verified bytes independent of host availability; forced attachment |
| ZIP export review | `POST /projects/:id/exports/preview` | `project.export`; `grant_id`; returns source manifest hash, paths, exclusions and consistency |
| ZIP export | `POST /projects/:id/exports` | `project.export`; `grant_id`, `idempotency_key`, reviewed `expected_manifest_hash`, `acknowledged_exclusions`; queued model-free job rejects changed source/unreviewed exclusions |
| Restore review/apply | `POST /projects/:id/restore/preview`, `/restore` | `checkpoint.restore`; checkpoint/grant, selected `paths` or null for whole, explicit `delete_extras`; apply additionally needs operation ID plus reviewed `expected_manifest_hash` and `plan_hash` |
| Quarantine/recover | `DELETE /projects/:id/files`, `GET /projects/:id/quarantine`, `POST .../quarantine/:qid/restore` | Separate `file.delete`/`file.restore` grants; delete checks expected hash; mutation IDs remain stable |
| Archive | `POST /projects/:id/archive` | Writer reservation; configuration only, preserves bytes |
| Unregister | `POST /projects/:id/unregister` | Existing native folder only; writer reservation; preserves bytes |
| Reactivate | `POST /projects/:id/reactivate` | Stable operation ID; retains existing IDs/history and uses the authoritative host transition |
| Environment | `POST /projects/:id/environment/restart|rebuild|remove` | Corresponding `environment.<verb>` grant and operation ID; trusted host configuration only |
| Protected data deletion | `DELETE /projects/:id/data` | `project.delete_data` grant, exact `canonical_root`, separate host `root_delete_grant_id`, operation ID; retained pre-checkpoint and recoverable quarantine |
| Writer reconciliation | `GET /projects/:id/writer`, `POST .../writer/reconcile` | Owner-only operation-ID match; terminal host evidence or atomic fencing before dispatch; job-held reservations use job recovery |
| Chat attachments | `POST/GET /attachments`, `GET /attachments/:id/download`, `DELETE /attachments/:id` | Owner/conversation/workspace checks, filename/base64, MIME sniffing; 16 MiB per file, 512 MiB retained owner quota; forced download and reference-retained soft deletion |

Saves take a non-expiring durable reservation. Transport loss retains `outcome_unknown`; expiry is never proof of rejection. The broker atomically validates the exact writer token and workspace revision, inserts the signed RPC and links its ID while holding the writer row. Reconciliation locks that same row. When no durable request exists, deleting the reservation atomically fences the paused old dispatcher before it can enqueue; when a request exists, terminal host evidence is required. Metadata publication also checks the current reservation. RPC options forward grant/tool scope for first-delivery revocation checks. Unknown conflicts do not release locks without explicit proof that effects never began. Checkpoint/export and managed command operations share the writer domain, with independent host-side exclusion. External desktop/local applications remain outside that domain: their conflicts are best-effort detection, not a filesystem transaction.

Restore application persists an immutable original intent before dispatch, so an identical retry sends the original precondition and byte hashes, rather than recapturing a new baseline. It captures before/after checkpoints and verifies resulting hashes/permissions. Selected restores preserve unselected later work. Extra deletion and file/directory type replacement require explicit deletion consent in the reviewed plan; incomplete captures and symlink restoration fail safely.

The injected `RootedHostFileAdapter` matches the Go supervisor wire format and verifies returned hashes. `AgentBroker` carries signed requests through the enrolled outbound mTLS channel; stable operation/RPC IDs, writer tokens and scope options must be forwarded. The local supervisor stays loopback-only. Do not publish its bearer-token endpoint or accept browser-selected transport addresses.

## Resumed storage implementation

The user resumed building. The earlier pause handoff is superseded; the planning pack remains unchanged.

Resumable transfers use `POST /projects/:id/uploads` with `{operation_id,grant_id,path,total_bytes,sha256,expected_sha256}`. The upload ID is the creation operation ID. Fixed 1 MiB chunks (last chunk may be shorter) go to `PUT /projects/:id/uploads/:uploadId/chunks` as `{offset,content_base64,sha256,grant_id}`. Maximum file size is 1 GiB, additionally bounded by protected host quotas. Status GET returns path, full hash, total bytes, contiguous-prefix `received_bytes`, disjoint `received_ranges`, state, expiry and original `commit_operation_id`. Completion POST requires a separate stable operation ID plus current grant. Unknown publication retains the writer reservation and original commit ID; it never becomes an ordinary cancelled staging session. DELETE cancels staging only. Metadata and range reads use `/projects/:id/files/metadata` and `/files/range`, with path/grant and bounded offset/length; chunks include hashes and total bytes. Clients verify the aggregate full-file hash before reporting download success.

Checkpoint capture now uses streamed host manifests and bounded ranges, retaining binary/untracked files without buffering whole files. Large restore stages immutable file bytes then sends one manifest-CAS `/restore-stream` batch; staging is not published by calling each upload completion separately. ZIP exports stream ZIP32 STORE entries with descriptors, validate retained full-file hashes, and enforce the configured 1 GiB retained stream-object bound including archive overhead. Artifact downloads verify retained bytes and stream them independently of host availability. Hard-link publication requires a protected local persistent filesystem with hard-link support: Linux production filesystems and tested local NTFS are suitable; Windows access through a WSL UNC share is unsupported. No non-atomic overwrite fallback is used.

Owner-only partial recovery has a metadata-only preview at `/projects/:id/writer/resolve-partial/preview?operation_id&grant_id` and reviewed POST `/writer/resolve-partial`. The POST requires original operation ID, distinct resolution ID, backend grant, separately configured protected host recovery grant, review ID, plan hash, reason and literal `resolution:accept_partial`. Reviews retain displayed manifest and original receipt, exact binding/revision/owner, and expiry. No content checkpoint is fabricated: preview checkpoint_id is null. The broker atomically consumes the dedicated review with the exact signed host body digest and original writer fence. The host rechecks the complete current manifest under its writer domain and appends an accepted-partial failure resolution; it does not roll back or rerun project mutations. Identical replay can finish backend reservation release after a lost response. Agent tools do not expose this action.

Reference-aware collection uses registry/publication triggers for checkpoints, artifacts, attachments, messages, jobs, job steps, inference requests, operations, file changes, log segments and explicit backup blob references. Collection and publication share per-hash advisory fences. An unreferenced object is marked nonlive durably before filesystem quarantine, and a second 24-hour grace period precedes deletion. Nonlive tombstones prevent late metadata from recreating references to missing bytes. Republish verifies bytes and reclaims old quarantine names; failed revival sources are rediscovered safely, including revival after a deleted tombstone. Collection refuses maintenance, restore and active backups. External encrypted restic archive hashes are not central blob references. `GET /storage/retention` reports retained states; owner POST `/storage/retention/collect` runs a bounded collection batch.

`GET /jobs/:id/log-retention` reports retained/expired-retained/unavailable log segments and audited expired segment counts. Owner DELETE with `confirm_expired:true` removes only already-expired segments from terminal jobs. Persisted job event/SSE byte records are independent retained evidence; this API does not claim to purge them. Other references and both grace periods can retain underlying bytes after segment metadata expiry.

`publishCheckpointChanges` links known before/after command checkpoints to idempotent, fenced file_changes and retained UTF-8 unified diffs or binary/large-file hash evidence. Files above 1 MiB are not loaded for text inspection. Attribution explicitly distinguishes recorded tool writes from unconfirmed observed project changes; no project diff proves all host-wide effects.

Generation boundary: the API initially joins the owned machine when loading a workspace and captures `machine_identity_generation` before awaited host calls. Rooted requests, binding/root discovery and receipt recovery forward that exact captured generation. Worker adapters use the immutable original job generation map, overriding any later lookup. The broker rejects absent/stale generations for enrolled hosts; replacing an agent never silently retargets an older operation.

Backup cut: writer acquisition locks runtime_control in share mode and rejects maintenance/restore inside the same transaction before claiming the workspace reservation. Blob publication also locks that control row before its hash fence. Attachment quota, bytes and metadata share one database client and transaction, avoiding pool starvation and preserving the fence through metadata publication. Operations must drain existing writers, processes, live jobs and uncertain RPCs before capturing the complete state.

Attachment library retention is explicit: `GET /attachments?include_deleted=true` exposes soft-deleted entries to their owner. `DELETE /attachments/:id/purge` requires an already-soft-deleted row, `confirm:true` and its exact `expected_sha256`. It removes library metadata and reports whether other references remain; frozen message/job/inference references continue retaining immutable bytes. Purging library metadata is not proof that physical bytes were erased.

Host staging is separately protected: default total stage budget is 2 GiB, charged for content plus inode/session/path/chunk metadata overhead. The pending-session count defaults to the bounded 100,000-entry manifest limit (configurable lower), so whole-project batches with more than 32 small files can stage without per-file publication. Host inactivity expiry is 24 hours with bounded cleanup; unknown workspace reservations prevent expiry cleanup of uncertain operation evidence.
